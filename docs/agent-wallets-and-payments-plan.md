# Phase 2 — Agent wallets, x401 proof, and x402 payments

## Release scope

An owner connects a Concordium wallet, selects a registered agent, and links a separate payment account to that agent. The agent can request a paid HTTP resource from a local or hosted runtime. Policy checks run before signing. The owner can see the charge and receipt, pause spending, and unlink or rotate the signer. A resource can independently require an x401 credential presentation before quoting or settling a payment.

Keep three independent trust decisions:

- **Agent identity** is the persistent CIS-8004 Agent Registry record. The current registry verifier, card hash, and wallet session establish the identity used by the lobby. The registry's reserved `agentWallet` metadata links the payment address, using the registry's proof-of-control procedure. Recheck that the agent is active and the binding matches before spending. Registry ownership transfer clears that metadata.
- **x401** is HTTP proof negotiation, not an agent registration or a payment scheme. Start with Proof’s version 0.2.0 draft and pin an exact revision before implementation, including `PROOF-REQUEST`, `PROOF-RESPONSE`, `PROOF-RESULT`, and the OpenID4VP/DCQL credential presentation it carries. A registry lookup alone cannot satisfy an arbitrary proof requirement. Confirm an issuer, credential format, holder, and independent verifier that interoperate before claiming Concordium ID support over x401. If native wallet proofs do not fit the credential exchange, evaluate a narrowly scoped, consented credential issued after independent Concordium proof verification. Define issuer trust and revocation explicitly.
- **x402** is HTTP payment negotiation. Use the upstream Concordium `exact` scheme and its sponsored transaction flow for native CCD or a supported Protocol-Level Token (PLT). The payer holds the quoted asset. The facilitator pays the network fee in CCD. Start with an explicit CCD quote in the pilot if the selected facilitator supports it, then verify a PLT quote separately. Marketplace listings and Protocol-Level Locks (PLL) for delivery-based escrow remain distinct from immediate x402 settlement.

## Initial compatibility checks

- Parsed Proof's public HTTP 401 example using `@proof.com/x401-node@0.3.3`. It returned a version 0.2.0 proof request with `openid4vp-v1-signed`. This confirms request parsing only. A real Concordium-backed presentation and third-party verification are still acceptance tests.
- Used `@x402/core@2.28.0` and `@x402/concordium@2.28.0` to round-trip v2 testnet quotes for explicit CCD and PLT amounts. The atomic amounts, asset identifiers, and facilitator-supplied sponsor survived HTTP header encoding. This check created no account, signature, or transaction.
- The scheme uses `ccd:9dd9ca4d19e9393877d2c44b70f89acb` on mainnet and `ccd:4221332d34e1694168c2a0c0b3fd0f27` on testnet. Native CCD uses six decimals. Read PLT decimals from the chain. Verify the selected facilitator's supported assets and sponsor address rather than assuming the upstream package defaults match a deployment.
- Current code already signs wallet login challenges in the panel and resolves CIS-8004 records in `packages/lobby-server/src/hosted/registry-roster-verifier.ts`. Marketplace authorizations in the lobby UI are wallet-signed messages. They do not sign or settle an x402 transaction.

## Product and security decisions

- Reuse the existing Concordium panel sign-in and registry verifier. Account connection is not account creation. Lead with **Connect an existing account** and **Create in Concordium Wallet**, then return to select the new address. The Wallet SDK can deploy a credential only with the required identity material. Treat embedded account creation as a separate capability that stays off unless the wallet can provide an authorized flow without exposing the owner's seed or identity secrets to Agent OS.
- Keep Agent ID ownership and payment custody separate. The owner approves the registry update and the dedicated signer proves control of the payment address. A configured address without a finalized binding is pending. A transfer or revocation disables spending until an authorized owner completes a new binding. Never reuse lobby session tokens as spend authorization.
- Default to zero spending. Set per-payment and period limits in base units, with explicit network, token, destination, and facilitator allowlists. Validate the complete transaction before signing. Never give model tools an arbitrary signing operation. Lock or reserve limits atomically, retain reservations for uncertain settlement, and reconcile with the facilitator and chain before retrying.
- Avoid credential or payment data leakage. Constrain destinations and redirects, block internal-network targets for remote requests and proof references, cap payload sizes, and keep keys, raw proofs, and headers out of logs. Store redacted audit records and public transaction identifiers. Require operator-visible state for approved, signed, pending, finalized, rejected, and uncertain outcomes.
- Use an isolated wallet and lobby for QA. Existing Agent IDs and the Phase 1 public swarm are outside the pilot. Testnet establishes repeatability. Mainnet acceptance uses dedicated, explicitly funded accounts and concrete authorized transfers.

## Funding guide to ship

1. Set up Concordium Wallet or Wallet for Web, complete identity verification, and create the human funding account. Verify the wallet network and copy its receive address.
2. For mainnet CCD, use a supported onramp or exchange from Concordium's directory. Check local availability and choose native Concordium for the withdrawal. Send a small initial amount and verify it in the wallet and explorer before sending more.
3. In the wallet, create or choose a separate agent account. In Agent OS, verify the selected address and network and finish the Agent ID wallet binding. For ordinary CCD transfers, use **Send** from the human wallet to that address, review the amount and fee, sign in the wallet, and verify finalization. Keep enough CCD in the sending account for fees.
4. For sponsored x402, fund the agent account with the asset the merchant and facilitator actually support. For native CCD, use the transfer in step 3. For a PLT quote, obtain the quoted token. Check the asset ID, issuer, network, any issuer restrictions, and token decimals. A CCD balance alone does not fund a PLT quote. Show the supported PLT acquisition and human-to-agent transfer steps once the pilot asset is selected.
5. Start with a low limit. Verify the first receipt against the chain, check the agent's remaining balance, and confirm that pausing the agent prevents further signing. Document how to recover funds using the approved signer or wallet recovery process before depositing additional assets.
