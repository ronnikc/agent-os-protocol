# AesirX CMP implementation and PR specifications

[Phase 3 plan](README.md) · [Product contracts](product-contracts.md) · [Pilot contract](pilot-contract.md)

Use separate implementation branches for the AesirX repos and open reviewable PRs for the owner to merge. Land inert capabilities behind flags before enabling them. Use synthetic data in fixtures and avoid publishing live credentials or deployment configuration. The owner controls repository approval and production enablement. External wallet and issuer approvals remain per deployment.

## Repository placement

- **Verifier/API integration.** Put the Phase 3 adapter, verified outcomes and DTS bridge in [aesirxio/verify-zkp-concordium](https://github.com/aesirxio/verify-zkp-concordium). Keep the existing Concordium ID App paths compatible. The public Google Wallet client calls a hosted AesirX endpoint. Its source repository was not identifiable from the available code search. Keep that endpoint for existing users and put the new Phase 3 Google adapter in the verifier facade using documented wallet APIs or an explicitly configured compatible endpoint. Confirm relying-party approval before enabling it. [CMP Google client](https://github.com/aesirxio/consent/blob/e1aa550c9dfa7ff1ad9a5c379271b7b4f0fece39/src/utils/walletVerify.ts) · [Google Wallet integration](https://developers.google.com/wallet/identity/verify/accepting-ids-from-wallet-online)
- **CMP actions.** Put the Phase 3 reference CMP service in a separate server package in [aesirxio/consent](https://github.com/aesirxio/consent). It owns the reference site's tenant-scoped consent record, outbox, linked agents and execution receipts. Use the existing CMP record through an explicit adapter when adding an existing site. Enable only after the adapter can read and update the site's authoritative decision and withdrawal state. Production CMP must not acquire a second competing authority for the same controller and purpose. The verifier facade receives proofs and returns verdicts. It does not own a site's consent state.
- **Site integration.** Package supported released CMP assets and server bridge in [aesirxio/wordpress-consent-plugin](https://github.com/aesirxio/wordpress-consent-plugin). Keep server protocol conformance shared with the JS deployment. Expose capabilities and stable errors to the optional Agent OS App via AO-1.

**Sequence:** pin AO-1A first. Verifier and CMP branches can build against its fixtures independently. Follow AX-2A with AX-2B and then the WordPress packaging PR. Keep the legacy verifier and human CMP behavior intact throughout. Enable per capability after the integrated run.

AX-1C starts against lifecycle fixtures without waiting for live issuer approval. AX-2C and AO-DeviceLifecycle consume that contract after the signer and CMP seams exist. Prepare CC-7's native recovery proposal early. Total-loss activation depends on approved enforceable authority and issuer continuity. New lifecycle capabilities are optional fields in versioned capability negotiation. Older clients continue their existing flow and cannot interpret a missing field as enabled recovery.

AX-WebSigner can build against the same contracts while lifecycle review proceeds. The first-time install-free visitor claim has its own fresh-browser and security evidence. A separate installed signer or previously connected wallet establishes only its tested journey.

**Owner review packet:** initial reference site, origin and tenant, API placement, exact base branches, tests with versioned shared fixtures, external provider approvals by profile, operational credential owner, consent enforcement and withdrawal evidence, independent rollback steps and the flag values to enable. The owner merges the AesirX PRs after review.
