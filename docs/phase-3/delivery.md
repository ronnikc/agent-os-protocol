# Phase 3 cross-repository delivery plan

[Phase 3 plan](README.md) · [Product flows and contracts](product-contracts.md) · [Concordium and DTS proposal](partner-proposal.md)

[DTS decisions](dts.md) · [Concordium PR specs](concordium.md) · [AesirX CMP PR specs](aesirx-cmp.md) · [Risk and gaps register](risk-and-gaps-register.md)

Use the first-party repositories and a local Concordium chain to deliver working code while external reviews are pending. Prepare the upstream implementation branches, tests and PR descriptions from the same fixtures so maintainers receive runnable patches. Use synthetic credentials in CI, real wallet sandbox evidence where access is available, and separate deployment flags for each externally approved capability. Keep the plan and evidence index in Agent OS Protocol. Publish upstream changes and share reviewer artifacts when the owner authorizes that step.

## Build and merge sequence

1. **Merge AO-1A first.** Publish the versioned [pilot contract](pilot-contract.md), executable fixtures and exact expected results as the source of truth. Pin genesis, SDK and node versions, issuer roles, signed x401 profile, site subject and race rules. Provide the local fixture runner and its reset. Start AO-1B and dependent repos against AO-1A. Keep vendor-neutral types in Agent OS.
2. **Build and test on the existing Concordium protocol.** Use the Local Stack test provider to complete identity request, issuance and credential deployment. Begin CC-1 and CC-2 from that fixture. In parallel build the AesirX wallet verifier and eligibility adapters in the selected verifier facade, and prototype Concordium Web3 ID issuance from external evidence for CC-5. Follow the Google implementation route in [AesirX PR specs](aesirx-cmp.md#repository-placement).
3. **Build CMP Agent ID and the App while issuer review is pending.** Use an existing Concordium test account for real register/link and cross-chain proof. Build server-side access and agent consent execution alongside the CMP workflow and Agent OS App. Agree the versioned fixture at the start of AO-1 to let both runtime and CMP changes land disabled and test against contract fixtures before enabling them together.
4. **Deliver reproducible native demonstrations to reviewers.** Run the CMP/App flow with a finalized native account from the local test provider. Independently verify the final token and delegated execution. Provide a separate Web3 ID issuance and revocation example and give DTS the policy mapping, handoff and test evidence for the first real profile. Ask for a confirmed test network and release-review window with compatibility evidence.
5. **Promote per capability.** Deliver approved native profiles through DTS on the existing protocol. Promote Agent ID linking and delegated consent on participating deployments after their evidence and review pass. Coordinate SDK/example delivery with P11 where possible. Open a consensus change candidate only under [3.6.1](sprint-3.6.1.md). Phase 2 owns PLL network activation and escrow.

Run rCuK against the local SDK signer as soon as the backup interface and recovery evidence fixtures are available. Integrate the restored-account test with finalized registry and delegation checks as those contracts land. Bring the reproducible restoration to Concordium as a provider-neutral example. Keep official-wallet integration and production approval independent of the first-party enrollment and CMP work.

Develop the [3.1.2 origin-ID device and recovery reference](sprint-3.1.2.md) from the same signer and enrollment fixtures. Deliver AO-DeviceLifecycle, AX-1C and AX-2C against the shared operation contract. CC-7 carries credential conformance and the native recovery-only authority proposal. Include second-device and total-loss results independently and report proof readiness and rejected old-device signing. CC-6 retains its independently reviewable retained-factor example. Follow conditional 3.6.1 for approved protocol implementation. [Lifecycle delivery and closure](origin-id-lifecycle.md#cross-repository-delivery-and-closure-evidence)

Build [3.1.3 AX-WebSigner](sprint-3.1.3.md) against the same signer contract so the CMP visitor path is independently testable without a local installation. Use existing compatible signer code where possible. Review browser isolation/storage and fresh-browser first use before advertising install-free native onboarding. Its full total-loss recovery evidence depends on the approved lifecycle authority.

## Reviewer packet and promotion evidence

- **Portable reproduction.** Record repository SHA, package versions, environment, config template, fixture files, exact commands, and which outputs come from real nodes, wallets or synthetic providers. Include screenshots or a trace of the user approvals, canonical finalized references, and an independent proof, card and payment check. Send no private identity evidence, secrets or historical concept attachments in the PRs.
- **PR independence.** Use a standard review brief with purpose, smallest diff, base and dependency SHAs, interface/version changes, test commands, security/privacy implications, feature flag and rollback. Reference review IDs across repos and track contract changes before promoting dependents. A reviewer should be able to run the upstream case without AesirX production services.
- **Approval matrix.** For each wallet and environment, track eligibility, DTS issuance, Concordium-derived credential prototype, and registry/agent proof separately. Record decisions from DTS, Concordium, the relevant relying-party or reader onboarding, and the CMP deployment owner. Record designated test custody and production authorization for any transaction. Document open blockers and which first-party release still proceeds.
- **Final gates.** Run the Agent OS identity, commerce, hosted, launch and sprint gates. Each AesirX and Concordium change runs its own host-repo tests and the shared interop fixture. Exercise proof revocation, owner/key change, lost wallet return, consent withdrawal, idempotent retry, rollback and unchanged prior behavior. Release broad access only after data and verification gates pass for that capability.
