# Draft proposal for Concordium and Digital Trust Solutions

**Owner review copy** — 17 November 2026. The work described here is proposed. No pilot result, issuer agreement, PR submission, or network slot is represented as approved. [Phase 3 plan](README.md)

[DTS integration brief](dts.md) · [Concordium upstream PR specs](concordium.md) · [AesirX CMP PR specs](aesirx-cmp.md) · [Risk and gaps register](risk-and-gaps-register.md)

## Decision requested

Build a single-approval enrollment path from an existing EUDI, Google Wallet or Apple Wallet credential to a user-controlled Concordium account using approved profiles. Start in AesirX CMP or Agent OS and return after the wallet handoff without forcing installation of a Concordium ID App or repeated document capture in the supported happy path. The operator separately reviews and authorizes a CIS-8004 Agent ID. Our initial request is a named DTS pilot owner and one accepted EUDI person-identification credential profile, then evaluation of a Google and an Apple candidate. Concordium can review the provider-neutral reference implementation on the current protocol and consider coordinating SDK and example releases with P11/PLL.

In AesirX CMP the operator can register or link a finalized Agent ID and the human can delegate a specific recorded consent instruction to that agent. The agent can relay the instruction and return an execution receipt, or ask the user for a decision when the scope changes. The Agent OS App, integration agent and skills install and verify the integration. A linked agent can remain on Ethereum, Solana or a supported network. CMP uses x401 for proof and x402 for independently approved payment.

Offer a narrow wallet proof when a site needs only eligibility. Native issuance is a separate opt-in with a preview of the fields DTS requires. In parallel, prototype a Concordium Web3 ID credential derived from external wallet evidence, with CIS-4 status and a tested holder and verifier flow. This lets Concordium evaluate scoped reuse of external proofs on its own credential infrastructure. Native account issuance and CIS-8004 owner authorization remain explicitly verified.

Include the full origin-ID lifecycle in the proposal. A user reuses the enrolled identity to add another device or recover the original account after every original device and personal recovery factor is lost. The same Agent ID remains owned by that account. Prepare a native recovery-only authority proposal where current credential rules cannot enforce lost-key replacement. DTS supplies the approved same-person continuity and private discovery contract. Concordium reviews the account-authority semantics and release scope. Account signing, promised identity proofs and rejection of old-device signatures have separate evidence. [Origin-ID lifecycle and authority proposal](origin-id-lifecycle.md)

For first-time CMP visitors, include AX-WebSigner's fresh-browser journey through existing-wallet approval, native account creation and first authorized use. Reuse a compatible reviewed signer or standard SDK in a dedicated signer origin. Record all prompts and review key/identity-material persistence and origin authorization before live use. This establishes the install-free outcome separately from the local separate-process reference. [Install-free signer sprint](sprint-3.1.3.md)

## Proposed reference flow

| Step | Responsible party | Evidence for review |
| --- | --- | --- |
| Begin enrollment | AesirX/Agent OS relying party and user-controlled signer | New operation contains relying-party origin, network, profile, purpose, key binding and pre-identity request digest. Account secrets remain with the signer. |
| Approve wallet presentation | Holder and wallet | Request displays the intended use. Presentation matches issuer, proof format, permitted claims, audience, holder and server-bound enrollment context. |
| Approve native issuance | DTS as approved ID provider | A profile-specific mapping defines accepted source claims, provenance, required fields and permitted fallbacks. An approved handoff delivers necessary attributes only to the authorized issuance component. Synthetic, labelled test approval is used in Local Stack. |
| Open and verify account | User-controlled signer and Concordium node | The existing identity object and account credential deploy successfully. Record time to finalized deployment, first account readback and first authorized use. A lagging serving node is reported separately and the operation resumes without duplication. |
| Add or recover a device | User signer, approved continuity service and enforceable account authority | Initial opt-in binds the account and recovery policy privately. Fresh same-person evidence authorizes the exact new device. Independently demonstrate device addition and total-loss recovery on the original account, old-device revocation and promised proof readiness. |
| Register agent | Account owner, CIS-8004 and optional CIS-8 | The owner authorizes the intended transaction. Finalized records match network, token, owner and Agent Card bytes. The public card carries only the public agent data and approved links. |
| Exercise access and delegated consent | CMP and separately operated verifier | The agent key answers a bound x401 challenge and the agent relays a recorded user decision for one controller and purpose. CMP records a separate execution receipt and denies changed-purpose or withdrawn use. |
| Exercise optional payment | Dedicated agent signer, merchant and facilitator | One approved x402 test payment is finalized and reconciled. A denied proof or replay triggers no additional transfer. |

For the local demonstration, use a supported reference wallet or reproducible synthetic presentation, one pinned issuer/verifier fixture and the Concordium Local Stack. The real-wallet and production gates use the same flow with the required approvals and rely on an explicit supported-profile matrix. Measure the prompts from our UI, the wallet, the provider and the signer. The UX goal is one identity presentation in the user's existing wallet and no duplicate onboarding capture where DTS accepts that evidence. The operator separately authorizes agent registration.

## What DTS would decide

1. Select the first issuing authority and supported credential/profile and define assurance, permitted attributes, and any extra liveness, fraud or identity checks. Specify cases that can complete without repeated document capture and the fallback for all other cases.
2. Choose verification by DTS or an expressly trusted verifier. Agree on the approved site/controller and relying-party registration or certificate, permitted claims and tenant/origin model. Define the signed handoff and which attributes, if any, DTS needs separately. Require binding to the verified genesis, stored pre-identity request, intended account signer and one-time holder approval. Agree on status checks, failure and step-up, recordkeeping, identity disclosure, retention and incident responsibilities.
3. Confirm the approved issuance interface, signer model, supported identity and signing-key recovery paths, and test environment. Agree the profile-specific pass/fail bar and review owner for a limited pilot. Record sample size, prompt and repeat capture, completion/fallback, processing time, status freshness and recovery criteria before enabling production.
4. Agree private same-person continuity and discovery after identity reissuance, including different holder keys, enrollment revocation, disputed recovery and issuer transition. Decide which recovery authorizers and compromise procedures can support the origin-ID lifecycle without a surviving personal wallet secret.

## What Concordium would decide

1. Confirm that DTS can use external wallet evidence while issuing the standard Concordium identity object and account credential. Name reviewers for the SDK example, test-provider adapter, and docs.
2. Confirm signer and wallet deployment paths, SDK, Base, connector and node versions, P11 test environment and review cutoff. Validate named-network and genesis-format compatibility with the actual verifier and wallet before advertising the new format. Agree how to measure finality, serving-node lag and first authorized use independently from cold bootstrap. Record the maintainer's review outcome before claiming the docs or tools are coordinated with PLL. [Base PR #986](https://github.com/Concordium/concordium-base/pull/986) · [JS SDK PR #711](https://github.com/Concordium/concordium-node-sdk-js/pull/711)
3. If direct protocol acceptance of external proofs is required, identify the maintainer and governance process for a scoped design. Agree on external trust and revocation, identity disclosure and recovery, deterministic verification, resource limits and deployment safety before discussing inclusion in the P11 release. The reference DTS path remains ready independently.
4. Review the Web3 ID derived-credential prototype and confirm if a participating issuer and current wallet surfaces can support it. Distinguish credential verification and status from native account admission or registry authority. Identify the smallest API or example PR justified by the demonstrated gap.
5. Review CC-7's credential conformance and native recovery-only authority RFC independently of new-account proof admission. Decide how same-account recovery replaces lost signing authority, including credential index 0, identity-proof material, fees, quorum takeover risk and deployment activation. Confirm official Registry sponsor coverage for registry operations and separately identify the payer for device/recovery operations.

Concordium has already published a high-level P11 lock SDK client and evolving lifecycle changes. The current release plan is best evaluated against the exact candidate revisions and the capabilities confirmed on the target network. PLL development does not need to absorb wallet-gateway behavior or issuer policy. [SDK Lock client](https://github.com/Concordium/concordium-node-sdk-js/pull/670) · [P11 lock support](https://github.com/Concordium/concordium-node-sdk-js/pull/673) · [Concordium roadmap](https://www.concordium.com/roadmap)

Routine eligibility uses minimal, context-bound decisions and profile-appropriate status checks. Where supported, shared signed status data lets verifiers refresh independently of individual visits. Test the supported self-hosted profile for no per-presentation callback to the original identity issuer or an AesirX central service. Enrollment, reissuance, identity disclosure and some recovery operations can involve other parties. [Bitstring Status List](https://www.w3.org/TR/vc-bitstring-status-list/) · [Concordium identity framework](https://docs.concordium.com/en/mainnet/learn/identity/index.html)

We will also include the independently reviewable local rCuK retained-factor restore demonstration and SDK example proposal. Its encrypted off-chain backup and test-chain policy commitment prove that reference's scope. The broader origin-ID lifecycle requires its own device and total-loss results. Ask Concordium to confirm supported backup/import and credential APIs, and DTS to clarify identity-object restoration versus issuer-assisted recovery. Production handling of wallet secrets requires independent cryptographic and operational review. [rCuK sprint](sprint-3.1.1.md) · [Origin-ID sprint](sprint-3.1.2.md)

## Draft PR order and acceptance package

1. **Issuer fixture and SDK example** — Concordium Base or Local Stack and the JS SDK. Link the changes but keep contracts reviewable on their own. Use standard deployment primitives and pin the example to supported versions. Provide one successful deterministic fixture and failure vectors for wrong issuer, wrong signer, altered issuance request, expiry and replay. [Local Stack](https://github.com/Concordium/concordium-local-stack) · [JS SDK](https://github.com/Concordium/concordium-node-sdk-js)
2. **AesirX backend and product adapters** — AesirX verifier facade, Consent JS and WordPress. Land the authenticated verifier seam before relying-party screens and plugin packaging. Document tenant, allowed origin, purpose and operation binding, disabled capabilities, and rollback. [Verifier facade](https://github.com/aesirxio/verify-zkp-concordium) · [CMP](https://github.com/aesirxio/consent) · [WordPress](https://github.com/aesirxio/wordpress-consent-plugin)
3. **Agent OS demonstration and pilot** — Wallet enrollment and eligibility, finalized registry handling, owner-installed CMP App and opt-in integration agent/skills, delegated x401 access, and optional x402 payment. Reproduce from a clean environment, with proof and payment results checked independently. Release controls stay separate for native issuance, optional autonomous credentials, payment and PLL.
4. **Concordium guide and conditional protocol work** — Publish a provider-neutral integration guide after confirming interfaces. If approved, submit the protocol design and separate Base, Node and SDK patches in that order. Gate consensus changes by the agreed activation rule and audit evidence, including legacy flow and PLL regression checks when bundled. [Concordium documentation source](https://github.com/Concordium/concordium.github.io) · [Concordium specifications](https://proposals.concordium.com/) · [Node](https://github.com/Concordium/concordium-node)
5. **Origin-ID lifecycle** — AO-DeviceLifecycle, AX-1C/2C and CC-7 supply private continuity, device UX, current-rule conformance and the native recovery-only RFC. Prepare the RFC early enough for the release-scope review. Carry any approved protocol implementation through CC-4 independently of external-proof new-account admission. Test the device and total-loss outcomes separately and leave the full product marked pending until both pass.

The final review package includes exact revisions and reproducible commands, wallet and issuer matrix, a captured accessibility and recovery walkthrough, public test-network or local finalized references where appropriate, redacted traces and negative vectors, trust/data-flow diagram, threat and licensing review, pilot enablement and rollback, and a record of the decisions above. Keep personal evidence and signing material outside shared artifacts.

The [delivery plan](delivery.md) defines each patch, the work that can be completed before approvals, and the test evidence each repository should carry.
