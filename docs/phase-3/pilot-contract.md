# Phase 3 pilot contract and conformance gates

[Phase 3 plan](README.md) · [Product flows](product-contracts.md) · [PR delivery](delivery.md)

This is the proposed baseline for AO-1. Sprint 3.0.0 turns it into a versioned contract release with executable fixtures. AO-1 owns the wire formats, canonical encodings, trust and status rules, expected results and changes to the profile. CMP and Agent OS runtimes consume the same pinned release and must pass its fixtures separately before enabling integration. Where this document requires a maintainer or issuer decision, the corresponding production capability remains gated.

## Pilot scope and relying parties

First prove a JavaScript reference site on the existing protocol using a local test issuer, local user-controlled signer, finalized CIS-8004 Agent ID, and delegated execution from a shared lobby. Run the same contract on WordPress before enabling the plugin integration, and add one separately authorized immediate x402 test settlement after access and consent pass. Production native issuance first uses one DTS-approved EUDI PID profile. Google Wallet and Apple Wallet rollout, the Concordium Web3 ID derived-credential example, additional external chains and conditional consensus development have independent gates. A confirmed P11 slot is not an entry requirement for any current-protocol capability.

For the first real wallet presentation, designate one site/controller, one verifier deployment and trusted origin, and a registered or approved relying party for that exact use. Record certificate or registration owner, permitted attributes, signing and encryption key custody, callback and response audience, holder binding, role responsibilities and allowed onward flow to DTS. A shared hosted verifier supports another site only after its exact tenant, origin, credentials or permitted hosting arrangement, callback and claims are approved. A site integration or certificate approval does not authorize a different origin or purpose. Keep test roots and production keys separate, and reject cross-tenant request and result substitution. [EUDI relying-party rules](https://eur-lex.europa.eu/eli/reg_impl/2025/848/oj/eng) · [OpenID4VP](https://openid.net/specs/openid-4-verifiable-presentations-1_0.html)

## Native issuer handoff and signer

For the initial local demonstration, use a separate user-controlled signer outside the page and the agent runtime. It handles pre-identity request creation, protected identity object storage, credential deployment and subsequent account signing. The CMP browser flow receives requests, public references and status. A hosted lobby or CMP page does not receive private signer material. Freeze the implemented signer and its storage, supported backup, device-loss restoration, rotation and authorization UX before 3.1.0 completes. Confirm the approved deployment model before exposing native production enrollment. A browser-embedded signer is a separate security decision requiring script isolation, key custody and recovery review.

[3.1.3](sprint-3.1.3.md) delivers the install-free CMP signer candidate behind that interface. Prefer compatible existing implementation and test a dedicated signer origin/top-level trusted surface with approved key processing and encrypted persistence. A fresh browser starts with no Concordium signer installed. Record actual approvals and complete first authorized use. The separate-process reference and existing-account CMP pilot retain their own gates. Enable the install-free production claim only after the browser path and signer review pass.

Select an EUDI Android reference wallet with the reference PID issuer and verifier and validate the ISO mdoc/OpenID4VP profile in 3.0.0. Run against the Local Stack test issuer first. On the first signer pairing, display the relying party, genesis and short comparison code generated by the local signer on a trusted user surface and match it to the protected enrollment session. The user approves the pairing and the wallet evidence for the selected issuer. The proof nonce and signed issuer assertion bind the signer key and pre-identity digest to that session. A relayed wallet response alone cannot substitute another target. Reuse a still-valid paired signer only under the same approved scope. Measure pairing and wallet-approval prompts independently. See the [DTS brief](dts.md) for national-profile and interface approval.

The signer provides the compatible local backup and restore interface for [Sprint 3.1.1](sprint-3.1.1.md). The [rCuK contract](product-contracts.md#rcuk-recovery-contract) requires a surviving independent user-held factor, separates any evidence used for eligibility from key release, and assigns chain state only the agreed commitment/status role. The routine-verification fixture measures issuer and service calls separately from enrollment, restore and reissuance.

The distinct [3.1.2 origin-ID lifecycle contract](origin-id-lifecycle.md) covers second-device enrollment and recovery with every original device and personal recovery factor absent. AO-1A freezes its protected discovery, operation/action/key/account binding, state/epoch concurrency rules, signer handoff, proof-material readiness and payer contract. Prepare the native recovery-only authority where the current protocol cannot enforce replacement. Existing-account CMP/App delivery proceeds under its own gate. Completion of that pilot or the retained-factor example leaves the full origin-ID lifecycle target pending.

The issuer interface needs an agreed, versioned evidence envelope. Start with a short-lived, signed, single-use verifier assertion for the DTS issuance endpoint. Bind issuer and audience, request ID and verifier session, relying-party identity and origin, approved evidence profile and assurance, asserted outcome and freshness, network genesis, canonical pre-identity request digest, intended signer key binding, and issuance purpose. DTS verifies the authenticated source and stored request, checks that its own issuance request matches the digest and signer proof, and makes the issuance decision. Exact required attributes and whether DTS needs the underlying presentation or attributes as well as the assertion remain profile-specific. When needed, deliver those items only to the authorized issuer or verifier through an approved protected handoff. Keep them out of the assertion metadata exposed to CMP or Agent OS.

Confirm holder authorization for the key-bound request using the chosen profile and signer UX. Verify both the original wallet holder binding and proof of control of the intended Concordium signer. Test relayed or swapped sessions, attacker-prepared signer requests, altered issuance payloads, wrong network, missing required fields and duplicate callback redemption. A generic eligibility proof cannot be redeemed as an issuance approval. DTS may request a documented step-up, or the user can finish a separately satisfied eligibility check. ## Network identity and compatibility

Resolve and validate the configured node's full genesis hash and derive its canonical CAIP-2 reference using the supported upstream SDK. Carry that network internally through pre-identity binding, issuer and verifier requests, registry coordinates and readback, delegated authority and x402 quote and transaction validation. Match all operations against the configured chain. Reject mismatches and ambiguous or malformed network input. Allow the legacy DID format at an explicit compatibility boundary only. Preserve existing persisted DIDs, including the Agent OS agent reference format, and resolve registry contract/token coordinates explicitly. Use the typed upstream DID parser for supported standard Concordium DID types rather than assuming it parses application-specific Agent OS agent references.

Concordium Base PR #986 was merged and JS SDK PR #711 was open on 17 November 2026. The SDK change covers genesis-prefix DID parsing and formatting, equivalent named networks, WalletConnect chain ID negotiation, and custom verification UI networks. Track merge, released versions, and the actual SDK/Base, node, wallet connector, issuer, verifier and indexer compatibility independently. Pin an exact revision for Local Stack experiments. Emit genesis-form DIDs only where counterparties support them. Production support uses the agreed released version and verified counterparty support. Named mainnet and testnet forms remain usable. The proposed SDK keeps mainnet key derivation and uses the testnet derivation convention for other networks. Distinct network identifiers therefore do not imply distinct signing keys. Test mismatched chains even with the same holder key and protect signing through explicit network binding. ## Authority and the controller's subject

Track lobby member, verified human subject or organization principal, authorizing representative, current registry owner, agent token and runtime holder key as independently verified roles. A member or registry owner cannot modify a privacy decision made by a different subject. An organizational representative can grant only the organization's authority within their role. Use the controller's existing authenticated account or protected browser session to establish the consent subject. The controller issues an opaque one-time approval reference scoped to its tenant, site, controller, subject context, purpose, notice and intended agent key, with expiry. The site stores the subject mapping and never accepts a global user identifier, Agent ID or caller-supplied subject as authority to change a decision.

The authenticated person reviews and records their choice at that controller and authorizes the named agent. A remote agent can submit the reference and its separately signed grant. The controller checks the human decision, agent holder proof, and server-side subject mapping at execution. Anonymous sessions may complete consent only while their protected binding remains valid, or after an explicit site-authenticated relink. The agent records the outcome under the scoped subject and actor but cannot invent or change the original choice. Executing a valid opt-in, refusal or withdrawal is a controller policy decision. The user's direct withdrawal remains available. The JS and WordPress integration must block applicable tracking before validated opt-in and while a request is pending, and stop covered subsequent requests after withdrawal. [EDPB consent guidelines](https://www.edpb.europa.eu/documents/guideline/guidelines-052020-on-consent-under-regulation-2016679_en)

## Signed x401 profile and race handling

Start with x401 0.2.0 and freeze its exact revision in AO-1. For the new local and hosted agent profile require signed OpenID4VP requests over x401 using the pinned mode, such as `openid4vp-v1-signed` where verified compatible. The holder validates verifier signature and identity, authorized destination, request expiry, nonce, DCQL and request binding before signing. Bind the response audience using the exact signed delivery mode. A relayed path has no browser-origin enforcement and requires verification of the signed verifier identity. Keep the Phase 2 unsigned pilot profile compatible with its existing fixtures and exclude it from new remote CMP mutations. Freeze an independently verified holder-bound credential profile, using the Phase 2 SD-JWT baseline as the starting point, and test issuance and proof separately from the delegation record. [x401 specification](https://x401.proof.com/spec/latest/) · [OpenID4VP](https://openid.net/specs/openid-4-verifiable-presentations-1_0.html)

AO-1 versions the challenge, credential and grant profile, pinned signature and issuer rules, expected audience and status strategy, and canonical digest for method, origin, resource, action, body where applicable, and policy version. Bind the grant to tenant, actor/key, authorized principal/subject reference, registry binding and network where applicable, scope, expiry and authority revisions. The server ties the fresh nonce to this context and returns a typed allow, deny, reapprove or reconcile result. The proof alone confers no execution authority. Conformance fixtures cover unsigned or substituted requests on the signed path, wrong issuer or site, wrong holder, replay, stale consent, malformed scope, incompatible network and duplicate requests.

Immediately before committing a CMP mutation or authorizing new payment signing, recheck current finalized registry status and owner, required key and wallet bindings, membership, grant and consent state within the pinned freshness rules. Fail closed on stale, unavailable or inconsistent authority. Registry state resolves to a verified block on the configured network. Consume the challenge and compare local authority revisions in the same transaction as the intended mutation or payment reservation. Order local revocation and execution by that commit. For external effects, record an idempotent outbox operation and recheck before dispatch. A public chain transfer cannot be atomic with a private database commit. Record the finalized block observed and the defined freshness and recheck window, and test a transfer that becomes visible before commitment. A cached proof never bypasses the checks. CIS-8004 transfer clears the token's external reference and agent wallet, invalidating the old bindings even if an external key registration still exists. Require explicit new bindings and grants with current owner approval. [CIS-8004 transfer semantics](https://proposals.concordium.com/CIS/cis-8004.html#transfer-semantics)

The new Phase 3 grant profile also binds the finalized account-authority fingerprint defined in the [lifecycle contract](origin-id-lifecycle.md#dependent-grant-invalidation). Key recovery can leave registry ownership unchanged. Recheck the actual credential/key/threshold state before new dependent execution or signing and require reauthorization after a fingerprint change. Test this with delayed recovery notifications and an otherwise valid old agent credential. Keep prior profile negotiation explicit.

Reserve shared budgets atomically before issuing signature authorization. Revocation, detected transfer or withdrawal blocks new signatures and dispatch under that authority. Release a demonstrably unsigned reservation where safe. If signing or broadcast already occurred, keep the reservation and reconcile that exact transaction and quote by finality, expiry and network state. Do not assume a signed payment can be canceled. A completed transfer retains its receipt, and any refund is a separate authorized operation. No retry can initiate a replacement payment while the original outcome is uncertain.

### Cross-service authority and revocation

| State | Authority for the pilot |
| --- | --- |
| Lobby membership and agent grants | The owning Agent OS lobby backend. Serialize removal, grant revocation, and new execution authorization against its authoritative revisions. |
| Human decision, controller subject and downstream state | The CMP controller backend for that tenant and purpose. It checks the exact consent version and records the mutation and outbox atomically. An existing pilot site must integrate its authoritative CMP store using the approved adapter. |
| Native ownership and wallet binding | The configured Concordium network, using finalized readback at or above the operation's prior observation and within the allowed freshness window. |
| Budget and payment | The tenant's Phase 2 spend ledger uses one shared atomic reservation per payment operation. A signer or facilitator cannot accept a model-supplied balance or bypass reservation and authorization. |

For each new cross-service mutation or payment signature, require a narrowly scoped, short-lived authorization from the owning lobby over an authenticated server channel. Request it at redemption, with intended method, action digest, tenant, grant revision and unique operation ID. No cached allow for another action or retry. Serialize authorization against revocation at the lobby. Use an initial maximum authorization age of 30 seconds and reject expired, repeated or mismatched results. A removal blocks authorizations ordered after removal. Already-authorized operations carry that ordering in their receipts and must still pass CMP's current decision and local commit checks. Before an asynchronous downstream dispatch or a new payment signature, recheck authority. Across independent systems this leaves a bounded in-flight window and does not promise instant cancellation. Record sequence/revisions and expiry. On an unavailable authority, deny new mutations, signatures or dispatch. Human inspection and direct withdrawal remain available at CMP.

Key the outbox to controller, subject, purpose and decision revision. Deliver repeated operations idempotently and apply only newer revisions at the supported downstream adapter. A late opt-in cannot overwrite an applied withdrawal. If the required adapter cannot enforce ordered withdrawal, keep that integration disabled. Retain uncertain payment reconciliation with the original reservation after revocation. Test dropped and delayed removal updates, partitions, mismatched grant revisions, withdrawal overtaking an opt-in and concurrent budget use.

### Official Registry sponsorship

Use the existing Concordium Registry sponsor relay and the owner-controlled wallet signature. On the supported public target, complete finalized mint and the necessary card update with a fresh zero-balance owner. Confirm each operation's coverage against the actual contract and service. Verify chain, sender, contract, entrypoint, exact payload and sponsor co-signature against the approved intent. The new signer must support the required sponsored send flow. Test sponsor decline and loss of response. Keep the finalized account and resume without duplicate mint. Offer self-pay only for a supported wallet with funds and an explicit fee review. Use a fixture sponsor for Local Stack. The official Registry sponsor is independent of the x402 payment facilitator or any optional rCuK publisher. ## Conformance and promotion

- **Shared lobby.** Three developers join one private lobby with distinct identities. A runs a local Claude agent, B runs a local Codex agent, and C uses a hosted agent. Each binds their agent to an approved scope. Link a site-authorized decision to the correct controller subject. Remove B while a B-agent request is in flight. Deny new B-agent operations after the revocation commit, retain A and C authority and unrelated public Agent IDs, reject cross-user substitution, and reconcile any already-signed payment. Test concurrent use of the same project's budget and isolation of personal privacy decisions from project permissions.
- **Pass or fail.** Local conformance requires all named positive and negative fixtures to behave as expected, no unauthorized operation or pre-consent tracking, no duplicate effect or settlement under replay, and verified supported recovery. The supported native happy path targets one identity approval, no forced app install and no repeated capture. Any deviations are recorded by wallet profile. Before a real pilot, pin sample size, allowed fallback and completion rates, stage latency or lag limits, revocation/status freshness, deployment and recovery targets, and operational stop conditions with the responsible partner. Report results even for capabilities that remain disabled.
