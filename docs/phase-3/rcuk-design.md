# rCuK reference recovery design

[Sprint 3.1.1](sprint-3.1.1.md) · [Product contract](product-contracts.md#rcuk-recovery-contract)

[Origin-ID lifecycle](origin-id-lifecycle.md) is the detailed 3.1.2 authority, continuity, state and delivery specification. It records current credential limitations and the proposed native recovery-only role. The factor model below applies to the retained-factor reference.

This is the design baseline for AO-Recovery on Local Stack with synthetic keys. Implement it in a separate user-controlled SDK signer process. Complete an independent cryptographic implementation review before handling real keys. The user must retain the enrolled factor even when the original device is gone.

## Origin-ID recovery target

The original rCuK product goal covers the full wallet lifecycle. After creating a Concordium account using an existing EUDI, Google Wallet or Apple Wallet ID, the user can reuse the **same underlying identity** to add a device or recover that account. Neither journey requires the user to enter or export a seed phrase or private key. [Sprint 3.1.2](sprint-3.1.2.md) tests both journeys. The 3.1.1 reference separately tests backup restoration with a surviving user factor.

**Add a device** by authorizing a fresh device key for the same account while preserving the existing devices. A current signer may confirm the new key where the approved policy calls for it. **Recover after loss** by authorizing a fresh device key after all original devices and user-held recovery factors are gone. Verify the same account and Agent ID and the status of old signing authority. Record these outcomes independently.

EUDI's architecture describes recovery and migration that can request reissuance of a PID or attestation to a new Wallet Unit. A reissued credential can use a different holder key. Actual recovery and reissuance depend on the Wallet and PID Provider. Reissuing an identity credential gives the user new identity evidence. Recovering an existing Concordium account also requires a surviving way to authorize that account or restore its signing keys. [EUDI trust model](https://github.com/eu-digital-identity-wallet/eudi-doc-architecture-and-reference-framework/blob/main/docs/main/06-trust-model.md#6543-migrating-the-pids-and-attestations-in-a-wallet-unit-to-a-different-wallet-solution) · [Concordium account credentials](https://docs.concordium.com/en/mainnet/technical-reference/wallets/guides/multi-credentials.html)

### Conditional design to validate with DTS and Concordium

1. **Enroll continuity while the account owner is present.** Record an issuer-approved recovery reference that lets the issuer or authorized continuity verifier confirm that fresh evidence is for the same enrolled person, scoped to recovery and protected off-chain. Do not assume a document number, wallet key, credential ID or proof hash persists across reissuance. Agree how the replacement app discovers the enrollment without anything from the old device and how renewals and issuer changes are handled.
2. **Authorize the new device.** After obtaining a fresh PID or equivalent approved origin credential, prove holder control and bind the request to a new device key, expected account, genesis, current recovery policy and a single-use challenge. The approved verifier confirms continuity with the enrolled identity and issues a narrowly scoped authorization. Evaluate assurance, additional checks, issuer compromise, replay, recovery notifications and disputes. A generic identity attribute or an age proof cannot establish continuity.
3. **Test continuity of the same account.** Prefer separate keys per device and pre-enrolled authority to rotate the account if the actual Concordium credential and threshold configuration can enforce the recovery policy. Existing threshold signatures may authorize ordinary account transactions too. Verify who can spend or modify credentials under the selected design before adopting it. Alternatively, independently operated recovery parties could release protected backup capability to the approved new device. That alternative changes the custody model from the reference pilot and needs explicit approval. Document what a colluding quorum or compromised issuer could do in either design. The identity presentation supplies authorization evidence and no encryption key material.
4. **Gate the claim.** The first successful origin-ID demo must start with both the original signer and all user-held recovery factors unavailable. It must use a newly issued credential for the same enrolled person, verify access to the original finalized account and preserve the linked Agent ID. Reject a different person, a valid but unlinked credential, wrong destination key or genesis, replay and stale or revoked policy. Confirm authority and compromise behavior before promising recovery for real funds.

Prepare the native recovery-only authority as the candidate for Concordium review, using the [current-rule conformance results](origin-id-lifecycle.md#product-outcome-and-current-constraints) to scope the change. A custody or archive-release alternative requires an explicit separate decision. The real authority and issuer trust model require DTS/Concordium and owner approval. Deliver the retained-factor reference independently while those questions are evaluated.

## Selected factor and storage model

| Component | Reference implementation |
| --- | --- |
| Wallet archive | Export only materials the pinned SDK signer needs to reproduce the account keys and, where compatible, the identity object and derivation metadata. Encrypt the archive in the signer. Verify original account signing and identity-proof readiness separately. |
| User factor | A recovery kit on a separately stored, user-controlled encrypted removable volume. It holds an independent random wrapping key U, a separate factor-authentication signing key and the recovery locator. Use the OS-supported encrypted volume and exercise an offline copy under the same user control. Users do not enter a wallet seed phrase. |
| Independent factor | One separately operated trustee process with its own keystore. It holds an independent random wrapping key T and separate update/approval credentials. The trustee releases only the user-encrypted intermediate envelope after a current policy read, factor proof and explicit trustee approval. Use a separate process and credential even in the demo. No AesirX-operated recovery custodian or cloud-synced passkey is required. |
| Recovery storage | A customer-managed store holds ciphertext and an opaque locator. The kit pins the locator, expected account and enrollment signing identity, trustee approval key, genesis and recovery contract. Enrollment includes actual archive readback and a test restart independent of the original installation. |

## Reference envelope and policy

1. In the local signer generate an independent archive key K with the system cryptographic RNG. Encrypt the wallet archive under K, then compute the digest of the complete encrypted archive. Encrypt K under U to create an inner envelope and have the trustee wrap that envelope under T over the trusted enrollment channel. Keep T in the trustee keystore. Keep U, K and the archive plaintext outside the trustee, CMP, lobby and agent runtime. Use maintained AES-256-GCM with a fresh nonce per encryption under a key. Authenticate version, layer purpose, recovery ID, genesis, policy epoch and a random archive ID in every layer. Authenticate the encrypted archive digest in the wrapping layers after the archive exists. Keep the unwrapped intermediate out of the backup and recovery kit. Use canonical field encoding and independently review production encryption and portable-kit packaging. [NIST authenticated encryption guidance](https://csrc.nist.gov/pubs/sp/800/38/d/final) · [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html)
2. Deploy a minimal Local Stack commitment contract for the fixture. Key its state by a random opaque recovery handle. The authorized publisher may advance the epoch monotonically using compare-and-set or mark the handle disabled. The off-chain canonical policy binds the recovery handle, expected account, genesis, epoch, archive digest, factor public key and trustee approval key. Publish only the epoch, active/disabled state and salted policy commitment. The original account signer, user factor and trustee approve enrollment and replacement in the private policy record. The relay publishes, and cannot create a valid replacement alone. When the original signer is gone, complete recovery under the current authorized epoch before changing it. The restoring signer validates the off-chain signatures and commitment against current finalized contract state. Keep the locator, identity evidence, account mapping, factors and ciphertext off-chain. Review publisher and issuance timing correlation separately.
3. On a clean device, use the recovered kit to locate the encrypted package. The user factor signs a one-time challenge bound to the epoch, expected account, verified genesis, archive digest, expiry and target device public key. The trustee verifies the factor, current finalized policy, new device proof and any approved eligibility evidence before consuming the challenge. Deliver the inner envelope through an authenticated channel bound to the target device, with a signed response covering the attempt and the target key. The target signer checks the response, uses U to unwrap K, decrypts the archive and verifies the resulting original account independently. No factor or archive material is sent to a browser page.
4. Validate freshness from a trusted finalized node and corroborate against the configured second source before service release. If policy reads disagree or current policy, backup or trustee is unavailable, recovery stays unavailable. A malicious or failed publisher can delay or deny recovery. After restore, revoke stale sessions, enroll fresh protection and verify the new epoch before retiring old service-held material. A party with a previously released inner envelope and U can decrypt an old backup offline. Chain revocation governs future release and cannot erase copies. Treat wallet-key compromise separately with supported rotation or asset migration. Recheck the Agent ID and each independent agent key. Keep paused grants, spending and settlement reconciliation separate from the restore.

## Evidence and gates

- Negative fixtures include trustee with ciphertext, user kit alone, wrong target device, wrong network, unauthorized update, disabled policy, stale epoch, corrupt archive, replay, and complete loss of the user kit. Independently verify that a valid identity predicate or registry record supplies no decryption key.
- Draw the recovery, identity-object and signer state diagrams separately. Measure account signing, identity-proof readiness and credential rotation separately. Check ordinary verification traffic in the supported self-hosted profile. Recovery itself can require a node, trustee and backup store, and issuer participation if identity material must be reissued.
- Track wallet-specific import support in the pilot record. Native production recovery, trustee-only recovery, cross-chain secret import and automatic key rotation are separate designs. CC-6 can use the test implementation as an example while production cryptographic, privacy and operations review remains open.
