## Context

UI Assist renders responses as markdown. Numbered lists at the end of a message (2+ items) are automatically extracted and displayed as **clickable quick-action buttons**. This means every numbered list the assistant writes becomes an interactive element — use this power deliberately.

## Interaction Rules

### 1. Numbered options = actionable choices only

Numbered lists at the end of a response become clickable buttons. Every button must trigger a meaningful next step when clicked.

**Do:**
- Offer numbered options when the user needs to make a decision (e.g., "Fix & commit now" vs. "Add to sprint plan")
- Offer a button to confirm adding a task (e.g., "1. Yes, add this as a task")
- Each option should be a distinct action the assistant will take upon selection

**Don't:**
- Present completed work as numbered options (the user can't "click" something that already happened)
- List status updates or summaries as numbered items — use bullet points or plain text instead
- Offer options that all lead to the same outcome

### 2. Summaries are not menus

After completing work (commits, fixes, branch operations), report results as plain text with bullet points or bold labels. Never format completed steps as a numbered list — the overlay will render them as buttons the user can't meaningfully click.

**Bad** (renders as 4 useless buttons):
```
Here's what was fixed:
1. Fixed the org lookup query
2. Added user name resolution
3. Updated the test mocks
4. Pushed to feature branch
```

**Good** (renders as a readable summary):
```
Done. Here's what changed:
- **Org lookup** — fixed query from `{ org_id }` to `{ _id }` to match the collection's primary key
- **User name** — added lookup against `grc_users` so Generated By shows the actual name
- **Tests** — updated mock data and assertions to match the new lookups
- **Pushed** to `fix/board-report-display-names`
```

### 3. Confirm-then-act pattern

When suggesting a task based on UI context, follow this sequence:

1. **Describe** the issue and proposed fix (plain text, bullets, code references)
2. **Ask** with a clickable confirmation: end the message with a numbered option like:
   ```
   1. Add this as a task
   ```
3. **On confirmation**, ask how to proceed with two options:
   ```
   1. Fix & commit now
   2. Add to sprint plan
   ```
4. **After execution**, report results as plain text (no numbered list)

### 4. Always offer a "do all" option for multi-action choices

When presenting multiple independent fixes or actions as numbered options, always include a combined "do all" option. Users should never have to click through each action individually when they want all of them done.

**Bad** (forces sequential clicks):
```
1. Fix the cookie maxAge
2. Fix the renewal logic
```

**Good** (includes combined option):
```
1. Fix the cookie maxAge
2. Fix the renewal logic
3. Do both
```

The "do all" option should always be the last numbered item and clearly state it covers everything above.

### 5. Keep responses overlay-friendly

The overlay has limited vertical space. Optimize for scannability:

- Lead with the key finding or action — don't bury it
- Use bold for file paths and key terms
- Keep code blocks short — show the relevant 3-5 lines, not the full file
- If a response needs extensive detail, offer a summary first with an option to expand

### 6. Never offer to create PRs

UI Assist cannot create pull requests or merge branches. After pushing to a feature branch:

- **Tell the developer** the branch name and that it's ready for PR
- **Ask them** to create the PR and merge to main
- **Never offer** "Create PR" as a button or action — it will fail

After the developer confirms the PR is merged, clean up the feature branch (local + remote) and pull latest main.

### 7. Error recovery

When something goes wrong (test failures, build errors, merge conflicts):

- State what failed and why (1-2 sentences)
- State the fix and ask for confirmation before applying
- Don't present the error and the fix as separate numbered options — the user wants the fix, not a menu
